# typed-resource-catalog — 2026-05-26

## hacking/ is the catalog's sorry

A `hacking/` segment in a TRC path is the analogue of Lean's `sorry`, Agda's `?`, and Coq's `admit`: a marked, addressable, closeable proof gap appearing as a literal directory name in the catalog tree @demoura2015 @norell2007 @coqteam2024.

Given a placement is a typing judgement — the schema at path $p$ asserts that the typed proposition $T(p)$ is inhabited by this schema, via type-as-proposition-as-object @curry1934 @howard1980 @lambek1969. Given by Lambek's fixpoint theorem @lambek1968, the chain of types from the root to $T(p)$ is unique up to unique iso once derived. Then a path of the form `Y/hacking/...` admits the claim "the chain from the root down to `Y` is derived; the chain from `Y` onward is open." The depth of the `hacking/` segment IS the size of the admitted gap.

A `hacking/` placed too shallow is a malformation. Given the placement-as-typing identification, a `hacking/` segment at `Y` asserts the chain to `Y` is derived; if proved ancestors below `Y` exist, placing `hacking/` at `Y` discards them. The segment must sit at the finest-true ancestor — the deepest position whose chain to the root is fully derived.

A path with an honest `hacking/` segment is strictly correct compared to a path that omits `hacking/` but sits at a wrong depth. The first tells the truth about its incompleteness; the second is a false typing judgement.

### Path-counting

Given each `hacking/` segment marks one unclosed derivation step, the count of `hacking/` segments on a path equals the count of open derivation steps that path admits. A path with three `hacking/` segments admits three distinct gaps. Multiplicity is precise gap-counting, not redundant marking.

### Closure trajectory

To close an open obligation, derive one further chain step beyond a `hacking/` anchor. Call the new derived intermediate `Z`. Two cases.

If the chain past `Z` is still not fully derived: rename `Y/hacking/library/X/` to `Y/library/Z/hacking/library/X/`. The `hacking/` segment moved one step deeper and the gap shrank by one step.

If the chain past `Z` is now fully derived: rename to `Y/library/Z/library/X/` with no `hacking/` segment. The obligation is discharged.

To audit, grep recursively for `/hacking/`. The total count of `/hacking/` segments equals the exact count of open derivation steps in the catalog.

Given the lattice of valuations $\mathbf{L}^{\bowtie\,\Phi}$ is complete and closure rules are knowledge-monotone @knaster1928 @tarski1955, each derivation step that deepens or removes a `hacking/` segment raises the corresponding obligation-cell in $\le_k$ from undecided to decided. Convergence is iteration to LFP across all obligations.

### Never raise the count

Adding a `hacking/` segment closer to the root throws away proved derivation. When placing `X`, push the `hacking/` segment as deep as derivation reaches.

### Failure mode

The recurring session failure: an agent internalizes "there is one hacking pile at the top" and either creates `X/` at the catalog root or places it under a shallow `hacking/library/X/` that ignores derived ancestors. The mental model is wrong. A `hacking/` segment is a path-segment placeable at any depth, possibly many times along one path, exactly where the math says one open step sits.

## Prose-doc placement

Prose-docs in the TRC live under a `$thing/docs/` subdirectory, sibling to the thing's `$thing.schema.json` and `$thing.jsonl`.

- `$thing/docs/$thing.md` — the thing's own prose. One per thing.
- `$thing/docs/dev/journal/$YYYY-MM-DD.md` — dev journal entries about the thing. One per date.

Given the per-thing rule (TRC §4) places each $thing's schema and log at the thing's directory, and given by the Yoneda embedding of the POSIX path category @yoneda1954 @maclane1971 the path is the categorical identity, prose about `X` must live at `X`'s path. Co-locating prose with the schema and log keeps a single Yoneda identity for the thing.

### Constraints

Each doc states the math and standards-conformance facts about its target directly. No meta-framing — no "curated out of," no "originally written by," no "the schema was left in place." One target per directory. One date per journal file.

### Why no central docs/ tree

A separate `docs/` tree at the catalog root would supply a second path for `X`'s prose, distinct from `X`'s own path. By the Yoneda embedding, the prose-at-root path bears a hom-functor built from the docs-root chain; the prose at `X/docs/` bears a hom-functor built from `X`'s own chain. These hom-functors are not naturally isomorphic, so the two paths present distinct categorical identities for the prose. The per-thing rule already co-locates schemas and logs at `X`'s path; co-locating prose there keeps documentation about `X` at `X`'s Yoneda identity rather than at a distinct doc-root identity.
