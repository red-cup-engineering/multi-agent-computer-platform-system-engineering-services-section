The **Typed Resource Catalog (TRC)** is SPOTCOMP's specific realization of a [positing-log](../../library/positing-entry/positing-entry.md#positing-log) as a typed-addressing system: the records of every typed resource in SPOTCOMP's substrate, with structural invariants on each EAVT position. A general "catalog" concept (any positing-log viewed as typed addressing, independent of substrate) is a separate proof obligation that sits above SPOTCOMP and is not derived in this note; this note derives the SPOTCOMP-specific POSIX+JSON-Schema realization.

## Invariants on EAVT positions

- The **e** position is always an **object** — a thing with a JSON Schema declaring its shape. (May or may not also have a script.)
- The **a** position is always a **transformer** — a thing with both a schema and a script. The schema specifies input and output types; the script executes the morphism.
- The **v** position is always an **object**.

A transformer is also an object (it has a schema), so a transformer may appear in `e` or `v` positions of rows about itself.

In the underlying math: an object corresponds to an element of the entity set $E$; a transformer corresponds to an element of the predicate set $\Pi$, the object-set of the predicate category $\mathcal{C}$. Each predicate $p \in \Pi$ indexes a fiber algebra $\mathrm{FOUR}^{E \times E}$.

## Operationalizability

A catalog becomes operationalizable as an executable closure rule-set when every `a`-slug in its rows has a backing schema and script. The current state has many `a`-slugs that lack schemas or scripts; the catalog is therefore a positing-log but is **not yet** executable as closure rules. The catalog densifies by adding a schema and script for each predicate encountered in the rows.

## Math object vs substrate object

The math-vs-substrate distinction runs throughout the catalog:

| math object | substrate object |
| --- | --- |
| positing-entry | eavt-row |
| bilattice-FOUR (the algebra) | the value encoding |
| predication-cell | the cell coordinate triple |
| positing-log | the jsonl files |

The map math-object → substrate-object is a realization morphism. Confusing the levels causes wrong schemas, wrong morphisms, and wrong derivations.

## Flatfile-Resource-Catalog (FRC)

The catalog's substrate is the **flatfile-resource-catalog**:

- **flatfile** — POSIX.1-2017 regular files with open/read/write/stat semantics;
- **resource** — a typed object with a JSON Schema (CHL: type = proposition);
- **catalog** — a typed-addressing system whose paths are identities (by Yoneda).

FRC = typed objects by categorical position as POSIX files. Each word is a precise technical claim, not decorative.
